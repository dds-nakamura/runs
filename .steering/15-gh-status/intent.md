# Intent: gh 経由で PR と CI の状態を画面に表示する

- 課題: #15 https://github.com/dds-nakamura/runs/issues/15
- 作成者: nakamura_kouji / 状態: approved
- 対象: TUI の画面（`ui` / `app`）、外部コマンドの起動（`runner`）、設定（`config`。必要なら）、キーバインド

## 課題（Problem）

- PR を出した後やマージした後に CI の結果を確かめるには、ブラウザか別の端末で `gh pr checks` / `gh run list` を叩く必要があり、runs の画面から離れる。
  #13 で CI を入れ、ルールセットで CI 通過がマージ条件になったので、「いま CI は通っているか」を見る頻度が上がった
- runs の構想（CLAUDE.md 冒頭）は「子プロセスの起動・出力・停止の仕組みを土台に、`gh` などの CLI 経由の PR / CI / 課題の確認を後から載せる」。その最初の段階がまだ無い
- 現状の runs には外部サービスの情報を取る経路が無い。`std::process::Command` を使うのは `runner` だけで、`App` はプロセスにもファイルにも触らないという方針がある（それを守る形で載せる）

## 目指す結果（Proposed outcome）

1. キーを 1 つ押すと `gh` を実行し、取得が終わると次が runs の画面に出る（2026-10-08 のユーザー回答）
   - open な PR の一覧: 番号・タイトル・ブランチと、各 PR の CI チェックの成否（成功 / 失敗 / 実行中 / 無し）
   - 最近の CI 実行（main への push を含む）の一覧: 対象ブランチ・結果（成功 / 失敗 / 実行中）・いつ
2. 取得は非同期で、取得中もコマンドの選択・実行・停止・出力の閲覧は止まらない。取得中であることが画面で分かる
3. `gh` が無い・未認証・ネットワーク不通・カレントディレクトリが GitHub リポジトリでない、のいずれでも、理由が画面に出て、他の機能は影響を受けない。runs の起動時には `gh` を呼ばない（キーを押すまでネットワークに触れない）
4. 表示は、`gh` の出力に含まれる制御文字が無害化されている（既存の `sanitize` と同じ水準）
5. 既存のキー（`↑↓ jk Enter s r PageUp PageDown End q Ctrl+C`）と設定ファイルの互換性が保たれる

判定: `runs` 自身のリポジトリで、PR を 1 つ開いた状態と main だけの状態の両方で、キー 1 つで上記 1 の内容が見られ、`gh` を PATH から外した状態では理由が表示されること

## 影響する利用者・環境

- 利用者: 開発者本人。`gh` 2.x を導入・認証済み（手元は 2.102.0）
- 対象 OS: Windows 11（Windows Terminal）/ Linux（WSL）/ macOS。`gh` の呼び出しと出力の読み取りは 3 OS で同じ動きが要る（CI の `cargo test` で守れる範囲は単体テストで、`gh` 実行は手元で確認）
- 取得先のリポジトリ: runs を起動したカレントディレクトリ（`runs.toml` のあるディレクトリ）が属する GitHub リポジトリ。`gh` の既定の解決に任せる

## 制約

- 外部サービスの API は直接呼ばない。`gh` CLI 経由のみ（CLAUDE.md）。`gh` の出力は `--json` で受け取り、人間向けの表形式はパースしない（`gh` の版で表示が変わるため）
- プロセスに触るのは `runner` だけ、`App` はプロセス・ファイル・端末に触らない、時刻は `set_now` で受け取る、という既存の方針を崩さない
- `gh` の実行はシェルを経由せず、引数を分けて渡す（`rust-safety` 6 章）。利用者の入力をコマンド文字列に連結しない
- 画面・CLI の文言は英語 ASCII。`println!` は使わない
- 表示する文字列（PR タイトル・ブランチ名）は信頼できない入力として扱い、制御文字を除去し、表示幅で切り詰める（`rust-safety` 3・4 章）
- 依存クレートの追加は spec で合意してから。JSON の読み取りに `serde_json` が要る見込み（現状の依存は `serde` + `toml` のみ）
- 設定ファイルに新しいキーを足す場合、`deny_unknown_fields` のため古いバイナリでは読めなくなる。足すなら任意キーにし、無くても動くようにする
- 一定間隔の自動更新は範囲外（後の課題。`needs_tick` の仕組みはあるが、API のレート制限と常時のネットワークアクセスの設計が要る）

## 範囲外

- 自動更新（ポーリング）
- issue の一覧、PR の作成・マージ・レビューなどの操作
- 複数リポジトリの切り替え（別課題）
- `gh` の導入・認証の案内（エラー理由を出すまで）

## 未解決の問い

- [ ] 表示場所: コマンド一覧と同じ画面に常時表示の区画を足すか、キーで切り替える別画面にするか、出力欄に流すか → ユーザーは「特に希望はない（spec で提案）」。画面構成の棚卸し（一覧欄 / ヘッダ 1 行 / 出力欄 / ヘルプ 1 行。区画を足すと 80x24 のスナップショットテストが一斉に変わる）を踏まえて spec で案を出す
- [ ] 取得に使うキー: 空いている文字キーは `a b c d e f g h i l m n o p t u v w x y z`、F1〜F12、Tab / Esc など。候補は `g`（gh）または `p`（PR）。spec で決める
- [ ] 「最近の CI 実行」の件数と、PR 一覧の上限（`gh pr list --limit` / `gh run list --limit`）。既定案は各 10 件。spec で決める
- [ ] `gh` を runner の既存の「コマンド」として起動するか、runner に `gh` 専用の起動経路（シェル無し・JSON 受信・1 回で完了）を足すか。方針「プロセスに触るのは runner だけ」は守る。spec で設計
- [ ] `gh` が無い環境（CI の `cargo test`）でもテストが通るように、`gh` の実行部分と JSON の解釈部分を分ける。解釈部分は固定の JSON で単体テストする。spec で設計
