# plan.md の作成（Build ステージ）

**計画が承認されるまでファイルを編集しない。** 設計レビューは文書を直すだけで済む段階で行う。

## 手順

1. プランモードでなければ EnterPlanMode に入る
2. `intent.md`・`spec.md` を読み、`impact-analyzer` で変更対象を確定する
3. 計画を作り、自分で次を問い直してから提示する
   - 何が壊れうるか／一番危険なステップはどれか／検討して捨てた案とその理由
   - 別プラットフォーム（cfg 分岐）や端末サイズの極端な値で壊れないか
   - この会話を見ていない人が plan.md だけで実装できるか
4. ユーザーとの質疑で詰め、承認されたら `.steering/<作業ディレクトリ>/plan.md` に保存する
5. 実装へ。実装中に計画から外れたら、**同じコミットで plan.md も更新する**
6. 独立した作業単位が複数あれば「並行可能」として分け、worktree（`claude --worktree <名前>`）で分担できることを伝える

## テンプレート

```markdown
# Plan: <件名>（spec.md <日付> より）

## 変更するファイル
- src/xxx.rs（変更）: <何を>
- src/xxx/tests.rs（新規）: <何を証明するか>
- Cargo.toml（変更）: <追加する依存と feature。spec で合意済みのもののみ>

## 作業順
1. <テスト（失敗することを確認）>
2. <実装>
3. <隣接箇所・ドキュメント・--help の文言>

## リスク
<壊れうるもの。cfg 分岐の片側漏れ、端末状態の復元漏れ、u16 座標のアンダーフロー、既存キーバインド・設定との互換>

## 証明（Proof）
- `bash .claude/scripts/verify.sh` が VERIFY OK
- <具体的なテスト名／描画スナップショット（端末サイズ）／CLI 実行と期待結果>
- <PTY での手動確認が必要な項目（あれば。誰が確認するか）>

## 並行可能な作業（任意）
## 捨てた案
```
