# spec.md の作成（Design ステージ）

## 手順

1. `.steering/<作業ディレクトリ>/intent.md` を読む（状態が approved でなければユーザーに確認）
2. 制約として読み込む（書きながら適用する。後からレビューで見つけるのではない）
   - `CLAUDE.md` の Conventions・Architecture・未確定事項（未確定事項に依存する設計は「懸念点」に挙げる）
   - `docs/` の設計書（あれば）
   - `rust-safety` スキル（エラー処理・端末状態・外部入力の表示・unsafe・依存追加に触れる場合は必須）
3. `impact-analyzer` サブエージェントで既存実装と影響範囲を調べる
4. 下のテンプレートで `spec.md` を書く。intent の「未解決の問い」は回答済みか、持ち越しかを明記する
5. ユーザーに「intent の課題を解決しているか」「懸念点」の確認を依頼する。承認後に /plan

## テンプレート

```markdown
# Spec: <件名>（intent.md <日付> より）

## 要件
### 機能要件（受け入れ条件）
- [ ] <Given/When/Then など判定可能な形で。キー操作と画面の変化で書く>
### 非機能要件
<描画・起動の性能、端末互換（OS・端末エミュレータ・最小サイズ・リサイズ）、色なし環境（NO_COLOR）、
 Unicode 幅（全角・絵文字）、終了時の端末復元>

## 設計
### 変更方針
<既存のどのモジュール・パターンに倣うか。状態（モデル）・更新（入力→状態）・描画を分ける>
### 型・状態遷移
<追加・変更する型、enum、状態遷移。公開 API の変更があれば差分のみ>
### 画面・キーバインド（該当時）
<レイアウトの概略、追加・変更するキー、既存キーとの衝突確認>
### 設定・CLI（該当時）
<追加する引数・設定キー・環境変数。既存形式との互換性>
### 依存クレート（追加する場合）
| クレート | 用途 | ライセンス | 代替案・追加しない場合 |

## 適用した規約・方針
| 規約・方針 | 適用内容 |

## 懸念点（要判断）
<方針同士が矛盾する・満たせない・未確定事項に依存する・情報不足の点。判断者を書く>

## intent の未解決の問い
- <問い> → 回答 / 持ち越し（理由）
```
